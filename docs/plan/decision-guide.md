# 编码分工决策指南

> **用途**: 当我（Hermes）面对一个编码需求时，按照这个流程快速决定谁来做
> **原则**: 能自己写就自己写，Aider 只做批量机械性工作，Kimi 做复杂逻辑

---

## 快速决策树

```
面对一个编码需求
│
├── 是否需要创建新文件？
│   ├── 是 → 我自己 write_file（Aider 创建新文件不可靠）
│   └── 否 → 已有文件上修改
│
├── 修改是否需要跨 3 个以上文件协调？
│   ├── 是 → 考虑 Kimi（交互式，能看到全局）
│   └── 否 → 继续判断
│
├── 修改量是否超过 50 行？
│   ├── 否 → 我自己 patch/edit（小改动更快）
│   └── 是 → 继续判断
│
├── 任务类型是以下之一？
│   ├── 批量字段改名/类型变更         → Aider
│   ├── 批量加注释/文档字符串          → Aider
│   ├── 在多个文件中重复添加相同逻辑   → Aider
│   ├── 写模板化的测试用例             → Aider
│   ├── 其他                         → 我自己写 或 Kimi
│   └── 
│
├── 是否有不明确的业务逻辑需要决策？
│   ├── 是 → Kimi（交互式，可以讨论）
│   └── 否 → 我自己写
│
└── 最终决策: 能自己写就自己写，不行再求援
```

## 快速对照表

| 任务特征 | 最适合 | 原因 |
|---------|--------|------|
| 涉及 1-2 个文件，修改 < 50 行 | **Hermes 直接写** | 最快，零开销 |
| 涉及 3-6 个文件，每处改动相似 | **Aider** | 一次改完，自动 commit |
| 涉及 3+ 个文件，每处改动不同 | **Hermes** 分步写 | Aider 会迷失 |
| 包含 `if/else` 业务决策 | **Hermes 或 Kimi** | Aider 容易选错分支 |
| 写测试用例（模板化） | **Aider** | 效率高 |
| 写复杂逻辑测试 | **Hermes** | 需要理解业务 |
| 重构 / 跨文件重命名 | **Kimi**（交互式确认） | 风险高，需人确认 |
| 新功能的第一版代码 | **Hermes** | 要确保架构一致性 |

## 执行策略

```
1. 先评估: 打开决策树，看属于哪一类
2. 自问: "这个我自己 3 分钟内能写完吗？"
   → 是 → 自己写
   → 否 → "Aider 做这个会不会迷路？"
        → 不会 → 调度 Aider
        → 会 → "需要和你讨论确认吗？"
            → 需要 → Kimi 任务
            → 不需要 → 我自己分段写
3. 验收: 无论谁写的，我都审查一遍（红线 + 路径 + import）
```
